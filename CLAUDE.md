# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DCUS Platform — a French-language Laravel 13 app for managing internal governance at a Beninese public institution (Direction de la Coopération Universitaire et Scientifique, under the Ministry of Higher Education): CODIR (comité de direction) meetings, "réunions", "décisions" (action items), and "accords" (agreements), with PDF/CSV export and role-based access. Views and domain vocabulary are entirely in French — keep new UI text, route names, and model fields consistent with that (e.g. `reunions`, `decisions`, `codirs`, `accords`, `utilisateurs`).

## Commands

```bash
composer install                 # PHP deps — requires PHP ^8.3 (see PHP version note below)
npm install                      # JS/CSS deps (Vite + Tailwind v4)

php artisan serve                # run app (http://localhost:8000)
npm run dev                      # Vite dev server (asset watch/HMR)
composer run dev                 # runs serve + queue:listen + pail + vite concurrently

composer test                    # clears config cache, then `php artisan test`
php artisan test --filter=Name   # run a single test
php artisan test tests/Feature/Auth/LoginTest.php

vendor/bin/pint                  # auto-fix code style
vendor/bin/pint --test           # check style without modifying (what CI runs)

php artisan migrate              # run migrations (see DB setup below)
php artisan migrate:fresh --seed # rebuild schema + seed default users
```

GitHub Actions (`.github/workflows/tests.yml`) runs Pint + the test suite (sqlite in-memory) on every push/PR to `master`/`main`.

### PHP version

`composer.json` requires `php: ^8.3`. If your local PHP (e.g. a XAMPP install) is older, install a standalone PHP 8.3+ (e.g. from windows.php.net) alongside it rather than upgrading XAMPP's Apache-bound PHP — the app is run via `php artisan serve`, not XAMPP's Apache/mod_php, so only the CLI binary matters. Needed extensions: `pdo_mysql`, `mysqli`, `mbstring`, `openssl`, `curl`, `fileinfo`, `gd`, `intl`, `zip`, plus `pdo_sqlite`/`sqlite3` for running tests (phpunit.xml uses sqlite `:memory:`). A standalone Windows PHP build typically ships with no CA bundle configured (`curl.cainfo`/`openssl.cafile` empty in `php.ini`), which makes any outbound HTTPS call (e.g. `GeminiClient`) fail with `cURL error 60: unable to get local issuer certificate` — fix by downloading `https://curl.se/ca/cacert.pem` next to `php.exe` and pointing both `curl.cainfo` and `openssl.cafile` at it in `php.ini`.

Default `.env.example` uses `sqlite`, but this app is developed against **MySQL** (`dcus_db`). `database/IMPORT_DB.md` documents importing the provided `database/dcus_db.sql` dump — that dump predates the CODIR/décisions tables (migrations `2024_01_01_000004` through `_000006`), so prefer `php artisan migrate:fresh --seed` over the dump for a fresh local setup unless you specifically need the dump's legacy data. ## Mail

Default mailer is **Brevo** (`MAIL_MAILER=brevo`), wired as a custom Symfony transport in `AppServiceProvider::boot()` (`symfony/brevo-mailer`) using `BREVO_API_KEY` from `.env` (a Brevo *API* key, `xkeysib-...` — not an SMTP key). The `MAIL_FROM_ADDRESS` **must** be a sender verified in the Brevo account, or sends are rejected. Brevo blocks API calls from unrecognized IPs by default; a new account's dashboard IP-authorization page is paid-plan-gated, but the automatic "Validate your IP address" confirmation email Brevo sends on first block works regardless of plan. Password-reset and CODIR/réunion convocation emails all go through this. Locally with no Brevo key configured, fall back to `MAIL_MAILER=log` to inspect emails in `storage/logs/laravel.log` instead of sending.

## Architecture

- **Routing**: all routes live in `routes/web.php`, no API routes. Nearly everything sits behind the `auth` middleware group; user management (`utilisateurs.*`) is additionally gated by `role:admin` via the custom `role` route middleware (`App\Http\Middleware\CheckRole`, aliased in `bootstrap/app.php`). Password-reset routes (`password.request`/`password.email`/`password.reset`/`password.update`, French URLs `mot-de-passe-oublie` / `reinitialiser-mot-de-passe`) sit under `guest` middleware.
- **Route keys are hashed, not raw auto-increment IDs** (explicit user request, to stop sequential IDs from being trivially enumerable in URLs): every model that's ever route-bound (`Accord`, `AccordAppreciateur`, `AccordAppreciation`, `AccordRapportConformite`, `Codir`, `CodirRapport`, `Decision`, `Reunion`, `ArchiveFolder`, `ArchiveFichier`, `ArchivePartage`, `ArchiveDossierPartage`, `User`, `UserInvitation`) uses the `App\Models\Concerns\HasHashedRouteKey` trait, backed by `App\Support\IdHasher` (a thin wrapper around `hashids/hashids`, salted with `config('app.key')` — no new `.env` variable needed). `getRouteKey()` encodes the real (auto-increment, unchanged) id for URL generation; `resolveRouteBinding()` decodes it back for implicit route-model-binding — an invalid/tampered hash decodes to `null`, so the lookup finds nothing and Laravel 404s normally, no special handling needed. This is why `route('accords.show', $accord)` (passing the **model instance**) has always been the required pattern in this codebase — passing a bare `$model->id` instead bypasses the encoding and leaks the raw sequential id into the URL. Laravel's `UrlGenerator::formatParameters()` applies this encoding to *any* `UrlRoutable` passed to `route()`, whether it lands on a declared `{param}` path segment or spills into the query string, so `route('archives.fichiers.create', ['dossier' => $dossier])` is equally safe — but `['dossier' => $dossier->id]` is not, since a bare int/string parameter is used verbatim. `Notification`'s own `{id}` (Laravel's built-in database-notifications UUID) and the password-reset/invitation-accept `{token}` (already random, opaque strings) were deliberately left alone — neither is a sequential id. Two call sites needed special handling beyond "just pass the model": `ArchiveController::createFichier()` reads `?dossier=` as a **query string** value (no `{dossier}` segment on that route, so no implicit binding applies) and must decode it manually via `IdHasher::decoder()`; and the Archives drag-and-drop JS (`archives/index.blade.php`) builds its `fetch()` URL client-side from a `data-id` attribute, so that attribute (and the sibling `data-dossier-id` used for the move-target body field, plus the `retour_dossier_id` hidden field feeding a post-share redirect) had to switch from `$model->id` to `$model->getRouteKey()`, with `ArchiveController::deplacerFichier()`/`deplacerDossier()` decoding the incoming `parent_id`/`dossier_id` body value back to a real id before using it (validation there changed from `exists:...,id` to a plain `string` rule, since it's no longer a raw id to check against the column). Deliberately **out of scope**: hidden/checkbox form fields that are pure body data and never become part of a URL (`parent_id`/`dossier_id` on folder/file *creation*, `dossier_ids[]`/`fichier_ids[]`/`destinataire_ids[]` on the share modal, `<select>` option values like a CODIR/decision "responsable" picker) — these still carry raw ids, since the request was specifically about IDs *appearing in links*, not every form field. Covered by `tests/Unit/Support/IdHasherTest.php` (encode/decode round-trip, garbage input decodes to `null`) and `tests/Unit/Models/Concerns/HasHashedRouteKeyTest.php` (a hashed key isn't the raw id, `resolveRouteBinding()` round-trips and rejects garbage, `route()` never emits the bare id as a path segment, an actual HTTP request with a tampered hash 404s) — plus every existing Feature test that hits a bound route was migrated from manually-interpolated `"/accords/{$accord->id}/..."` URL strings to `route('accords.xxx', $accord)` calls, since the old string form now points at a URL nothing resolves to.
- **Roles**: plain string column `users.role` (`admin` / `secretaire` / `agent`), checked via `User::isAdmin()`, `isSecretaire()`, `isAgent()`, `canManage()` (admin or secretaire). Authorization for the CRUD resources (Accord, Reunion, Decision, Codir) goes through Laravel **Policies** in `app/Policies/` (auto-discovered by naming convention, no manual registration) called via `$this->authorize(...)` in controllers — `create`/`update`/`delete` map to `canManage()`; `CodirPolicy` additionally has `administer` (admin-only: rapport upload/delete, access grants) and `download` (admin OR a per-user `CodirAcces` grant, see below). User-management routes still use the `role:admin` middleware rather than a policy (whole-route-group gate, not per-resource). Blade views still call the `User` model helper methods directly for show/hide UI logic (not `@can`) — that's presentational only, the real enforcement is server-side in the policies/middleware.
- **Auth**: session-based via `Auth::attempt` in `AuthController`; login additionally checks a `users.actif` boolean and force-logs-out disabled accounts. Login is rate-limited (5 attempts / 60s lockout, keyed by email+IP via `RateLimiter`, mirrors Laravel Breeze's pattern) — see `AuthController::ensureIsNotRateLimited`.
- **User onboarding is invite-only**: there is no self-serve signup and no admin form that sets a password directly. An admin picks an email + role on `utilisateurs/create` (`UserController::store`), which creates a `UserInvitation` row (email, role, sha256-hashed token, `invited_by`, `expires_at` = +7 days — *not* the same token mechanism as password resets, since there's no `User` row yet to attach a broker token to) and emails an on-demand `UserInvitationNotification` (no `Notifiable` model involved: `Notification::route('mail', $email)->notify(...)`). The invitee follows `/inscription/{token}` (`RegistrationController::show`/`store`, `guest` middleware) and supplies nom/prénom/service/password themselves — role and email come from the invitation, not the form. On success the invitation row is deleted and the new `User` is logged in immediately. Admins can resend (regenerates the token + expiry) or revoke pending invitations from the same "Invitations en attente" section on `utilisateurs.index` (`UserController::renvoyerInvitation`/`revoquerInvitation`, also `role:admin`-gated). `User::$services` holds the 4 valid `service` values (`SA`/`SAF`/`SSCP`/`SISCUAP` — short codes stored, `service_label` accessor for the full French name); the column is nullable since users created before this feature existed have no service set. `users.telephone` is edited from two places — `utilisateurs/edit.blade.php` (admin editing another user, `UserController::update`) and `profile/edit.blade.php` ("Mon profil", `ProfileController::update`) — both validated `'nullable|digits_between:1,20'` (Laravel's built-in `digits_between` rule, not a custom regex — digits only, no `+`/spaces/dashes, per explicit user decision; the registration/invitation-acceptance form has no telephone field at all, so this restriction only applies post-onboarding). Existing rows with a pre-restriction value (e.g. a `+229 ...`-formatted number, or anything from `UserFactory`'s Faker-generated phone strings) are left as-is — the rule only gates new submissions through those two forms, there's no data migration/cleanup of legacy values. Covered by `tests/Feature/Auth/TelephoneRestrictionTest.php`.
- **Core domain models** (`app/Models`): `Reunion` (meetings) and `Codir` (CODIR sessions) are largely parallel concepts — each has its own `statut` enum-like array (`$statuts`/`$statutColors` static props + accessors), participants/decisions relations, and its own PDF export flow. `Decision` (action items) can originate from multiple source types (`codir_interne`, `codir_externe`, `reunion_interne`, `reunion_externe`, `note_ministerielle` — see `Decision::$sourceTypeLabels`) and polymorphically-ish links back to either a `Codir` or a `Reunion` via nullable `codir_id`/`reunion_id`. `AccordHistorique`/`DecisionHistorique` are audit-trail side tables. `Accord` is documented separately below — it does **not** have a manual `statut` column or a `reunion_id` link (both were removed in the workflow rework).
- **Accords — workflow DCUS (réception → appréciation → envoi → signature)**: `Accord` has no stored `statut` — its `etape` (`recu`/`apprecie`/`envoye`/`signe`, `Accord::$etapeLabels`/`$etapeColors`) is a **computed** accessor derived from which columns are filled (`appreciation` relation exists, `envoye_le` set, `date_signature` set), so it can never drift out of sync. `AccordHistorique` was reworked the same way: instead of `ancien_statut`/`nouveau_statut` transitions it now logs free-text `evenement` strings ("Accord reçu", "Appréciation enregistrée par X", "Signature enregistrée", ...). Both the `accords` and `accord_historiques` migrations were edited **in place** rather than layered with new ALTER migrations — safe only because the project had no real operational data yet (per the Database section); this required a `migrate:fresh --seed` when the rework shipped, which is *not* safe to repeat once real data exists.
  - **Étape 1 (réception)**: `AccordController::store` — admin/secrétaire only (`AccordPolicy::create` = `canManage()`). `date_arrivee`/`heure_arrivee` default to "now" server-side when left blank. The uploaded file (`chemin_fichier`/`nom_fichier`) lives on `Storage::disk('public')`, mirroring the Archives upload pattern.
  - **Étape 2 (appréciation)**: a *separate* permission, not `canManage()` — `AccordPolicy::apprecier()` / `User::peutApprecierAccords()` allow admin/secrétaire **or** any user explicitly listed in `accord_appreciateurs` (a flat, global "authorized to appreciate" grant, not per-accord — different from `CodirAcces` which is per-CODIR; managed by admins at `accords.appreciateurs.*`, `role:admin`-gated same as `utilisateurs.*`). `AccordAppreciationController::store` uses `$accord->appreciation()->updateOrCreate([], $data)` so re-submitting **edits** the single existing appreciation rather than creating a second one (one appreciation per accord, by design — the form fields are Origine/Objet/Avis/Observations sur la forme/Observations sur le fond). **`avis` is the fiche's unique identifier (a short number, e.g. "0053"), not the conclusion/recommendation text** — it fills the blank after "Avis N°" at the top of the generated document (`Avis N° {avis} /MESRS/DCUS/{année}`); this was an explicit user correction after an earlier version wrongly treated `avis` as free-form judgment text feeding the boxed **Conclusion** paragraph. The Conclusion itself is **not** a form field at all — see `Accord::$conclusion_appreciation` below. Saving generates a `.docx` via `App\Services\FicheAppreciationGenerator` (`phpoffice/phpword`, direct `PhpWord` object construction — not `TemplateProcessor`, since the DCUS never supplied an actual `.docx` template file, only real example fiches) and stores it in `chemin_fiche_word`, deleting the previous file on re-submission. The generated document reproduces the real DCUS layout observed across those examples. **The ministry letterhead is not a table** (explicit user correction) — `FicheAppreciationGenerator::ajouterEnTete()` inserts `resources/images/logo-mesrs.png` (262×60pt, matches the source file's ~4.37:1 aspect ratio) as a **floating** image, anchored top-left of the margin (`wrappingStyle: square`, `positioning: relative`, `posHorizontalRel/posHorizontal: margin/left`, `posVerticalRel/posVertical: margin/top`), followed by six separate right-aligned (`Jc::END`) paragraphs for the contact info ("Cité Ministérielle-Bâtiment F", "Qtier Ahouanlêko, 12ème Arrondissement", "Adresse postale : 01 BP 348 Cotonou", "Téléphone : +229 01 21 32 88 63", "contact.mesrs@gouv.bj", "www.enseignementsuperieur.gouv.bj" — updated to match the real MESRS letterhead observed on the reference fiches, see below) plus the date line — no tab stops anywhere. Floating the image takes it out of the normal text flow, so the right-aligned paragraphs start at the same vertical position (page-margin top) as the image instead of stacking below it — this is what actually puts the logo and the contact block on the same header "row". An earlier version used a plain **inline** (non-floating) image instead, on the reasoning that inline was inherently safer than the floating/tab-stop technique that had caused overflow before that — but a direct visual check (rendering the generated `.docx` to PDF via Word COM automation, `powershell.exe` + `Word.Application` COM object, then to PNG via the `Windows.Data.Pdf` WinRT API, and reading the PNG) showed the inline image and the right-aligned text starting at clearly different heights, since each inline image is its own paragraph in the normal flow — an unbalanced, not-actually-aligned header, which the user caught and asked to be fixed by visual inspection ("regarde toi-même"). The version *before that* floated a bare coat-of-arms image with `wrappingStyle: square` and put "MINISTÈRE / DE L'ENSEIGNEMENT SUPÉRIEUR / ET DE LA RECHERCHE SCIENTIFIQUE / RÉPUBLIQUE DU BÉNIN" beside it via four `addTextRun` paragraphs each carrying a right tab stop (`PhpOffice\PhpWord\Style\Tab`) — the tab position (9350 twips) exceeded the usable page width under *default* 1440-twip margins, which silently truncated the contact info at the right edge (confirmed by the user's own test print). The current approach floats the image (for alignment) but keeps the contact-info paragraphs as plain `Jc::END`-aligned text with **no tab stops** — `Jc::END` always clamps to the real right margin dynamically, unlike an absolute twip tab position, so it carries none of the old overflow risk while still achieving the side-by-side layout. The section is still built with reduced margins (`marginTop: 600, marginLeft/Right: 900, marginBottom: 900` twips, vs. PhpWord's 1440-twip/1in defaults) so the letterhead sits closer to the true top of the page, per the user's original feedback that the default felt too far down; `LARGEUR_CONTENU = 10000` is now used only for the table below (kept **inside** the resulting usable width, page ~11905.5 twips − 900 − 900 ≈ 10105, for the same reason the old tab position needs to fit). **On the logo file itself**: the first two files the user pointed at (both confusingly named `logo MESRS.png`/`logo-ministere.png` at the time) actually turned out branded for a *different* ministry (METFP — "MINISTÈRE DES ENSEIGNEMENTS SECONDAIRE, TECHNIQUE ET DE LA FORMATION PROFESSIONNELLE"), flagged to the user each time; the third file supplied (`logo.png` in Downloads, copied in as `resources/images/logo-mesrs.png`) is correctly branded — armoiries + "MINISTÈRE DE L'ENSEIGNEMENT SUPÉRIEUR ET DE LA RECHERCHE SCIENTIFIQUE" + "RÉPUBLIQUE DU BÉNIN" — and is the one actually wired into the generator now. `resources/images/armoiries-benin.png` (an even earlier, correctly-branded but bare coat-of-arms image, from before any combined-logo file existed) is no longer referenced by any code but was left in the repo rather than deleted. The `Avis N° {$appreciation->avis} /MESRS/DCUS/{année}` line is filled directly from the form's `avis` field (see above — this used to be left blank for hand-writing before that field's real meaning was clarified); the fixed `Arrêté 2022 N° 0145/...` legal reference follows; the title is built as `"FICHE D'APPRÉCIATION DU PROJET D'".$accord->titre` (so `Accord::titre` must itself read as a full sentence starting with "Accord..." and naming both parties — the reception form's help text prompts for this phrasing). **Everything after the title is one single bordered table** (`addTable`, one row per field) — Origine, Objet, Référence (`$accord->reference` + `$accord->date_arrivee`, not re-typed), Destinataire (always mirrors Origine, matching all three samples, per explicit user decision rather than a separate field), "1°) Observations sur la forme", "2°) Observations sur le fond", and Conclusion — per an explicit user correction: these used to be four separate one-row tables plus untabled observation paragraphs plus a separate conclusion table, which didn't match the real fiches. **The Conclusion is not user-supplied at all** — a second, later user correction clarified that `avis` (above) is just the fiche's identifier, and that the Conclusion must instead be generated automatically from a fixed DCUS-mandated template, with only the accord's own description varying: `Accord::getConclusionAppreciationAttribute()` (`$accord->conclusion_appreciation`) returns `"Au regard de tout ce qui précède, le processus de signature de l'".Str::lcfirst($this->titre)." peut être enclenché, sous réserve de la prise en compte des observations faites."` — relying on the existing convention that `Accord::titre` always reads as a full sentence starting with "Accord..." (e.g. "Accord-cadre de partenariat entre les Camiltiens et l'UAC"), so `lcfirst()` plus a prefixed "de l'" produces correct French elision ("de l'accord-cadre..."). `FicheAppreciationGenerator::ajouterLigneConclusion()` takes the `Accord` (not the appreciation) and reads this accessor directly — there is no way to override it per-fiche. The intro sentence ("Dans le cadre de l'objet suscité...") lives **inside** the "Observations sur la forme" cell, as that cell's first paragraph (passed as an `$introduction` argument to `ajouterLigneObservations()`) — per explicit user correction, it used to be a standalone paragraph before the table. Within the two observations rows, `FicheAppreciationGenerator::ajouterParagraphes()` (shared via the `App\Services\Concerns\RendDesParagraphesAvecPuces` trait, typed against `AbstractContainer` so it works on both a `Section` and a table `Cell`) parses a lightweight convention line-by-line: a line starting with `-`/`•`/`*` becomes a real PhpWord bullet (`addListItem`, `w:numPr`/`w:ilvl` in the docx), with 2 leading spaces before that marker bumping it one sub-level deeper (capped at depth 3); a line with no such marker stays a plain paragraph (`addText`). Covered by `tests/Unit/Services/FicheAppreciationGeneratorTest.php`, which unzips the generated `.docx` and asserts on `word/document.xml` text, `w:ilvl` depth values, that exactly one `<w:tbl>` exists in the document and no `<w:tabs>` element exists anywhere (regression guard against the truncation bug), that it appears after the contact-info text (i.e. the header truly precedes the table), that the reduced margins are present, that the intro sentence falls inside the table and before "1°) Observations sur la forme", and the presence of an embedded image under `word/media/`. On `accords/appreciation.blade.php`, Avis (the fiche identifier) is a short `col-md-4` text input, not a textarea — there is no Conclusion field in the form at all, since it's fully computed (see above). The two observation fields are each full-width and collapsed behind a clickable Bootstrap `collapse` toggle button (auto-expanded if they already hold a value, e.g. when editing) revealing a 16-row textarea — the earlier side-by-side 4-row textareas were reported as too cramped to comfortably write in. The "Générer avec l'IA" JS (see below) explicitly expands both collapse panels via `bootstrap.Collapse` after filling them, so AI-suggested content is never hidden behind a collapsed toggle; that same JS does not touch the Avis field (the AI never suggests the fiche identifier — a human-assigned number, not content).
  - **Deux institutions, pas une** : an `Accord` has two separate institution fields — `institution_origine` (the Beninese university that *initiates* the accord, e.g. "UAC"; added later than `institution_partenaire`, via an additive migration since real accords already existed by then — `2024_01_01_000020_add_institution_origine_to_accords_table.php`, nullable so pre-existing rows aren't broken, required going forward via controller validation) and `institution_partenaire` (the other party, e.g. "Université Paris-Saclay", present since the original `accords` migration). Both are plain required text inputs on `accords/create.blade.php`/`edit.blade.php` and both appear on `accords/show.blade.php` — neither is derived from the other, and neither is the same field as `AccordAppreciation::$origine` (the appreciation form's own "Origine" input, filled independently by the appreciating agent, even though it's typically the same institution as `institution_origine` in practice).
  - **Liste et filtres** (`accords.index`, `AccordController::index`): the four étape stat cards at the top (Reçu/Apprécié/Envoyé/Signé) are clickable filters, not just a passive summary — each links to `route('accords.index', ['etape' => $key, ...])` (preserving every other active filter via `request()->except(['etape', 'page'])`, dropping `page` so changing the filter resets pagination), and clicking the currently-active one toggles it back off. The étape filter reuses the exact same query conditions as `$etapeCounts` (`doesntHave('appreciation')` / `has('appreciation')->whereNull('envoye_le')` / etc.) via a `match()` on `$request->input('etape')` — note `$etapeCounts` itself stays unfiltered (always the global breakdown), only the list query is filtered, so the four numbers never change based on other active filters. Four more filters sit in the search form: institution d'origine (`institution_origine`, exact match) and institution partenaire (`institution`, exact match — the query-param name doesn't match the column name, kept as-is since it predates the `institution_origine` field and renaming it would be a pointless breaking change to bookmarked/shared URLs) are both `<select>` dropdowns populated from `Accord::distinct()->pluck(...)` — dropdowns rather than free text so they can't typo-miss existing values — plus a date-arrivée range (`date_debut`/`date_fin`, `whereDate('date_arrivee', '>=' / '<=', ...)`). The search form carries a hidden `etape` input so submitting it doesn't silently drop an active étape filter (a plain GET form replaces the whole query string with only its own named fields). Covered by `tests/Feature/AccordListFilterTest.php`.
  - **Confirmation par mot de passe** : `AccordController::update()`/`destroy()` require the acting user's own current password on every submission (`'password' => ['required', 'current_password']` — Laravel's built-in `current_password` rule, checked against the authenticated user, no custom logic needed), re-asked on every single request with no grace window/session timer, per explicit user decision — deliberately scoped to just editing/deleting the `Accord` record itself, not `envoyer`/`signer`/appreciation edits (those were explicitly excluded when scoping this feature). The edit form (`accords/edit.blade.php`) has a plain password input at the bottom of the same form; the destroy action switched from a bare JS `confirm()` dialog (which can't collect a password) to a Bootstrap modal (`#supprimerAccordModal`, same modal pattern as `decisions/index.blade.php`) with its own password field — present on both `accords/show.blade.php` (one modal, one accord) and `accords/index.blade.php` (one shared modal reused for every row: each row's delete button rewrites `#formSupprimerAccord`'s `action` via a small inline `onclick` before opening it, rather than emitting one modal per row). The list page's delete button was initially left on the old `confirm()` pattern when the password requirement first shipped, which silently broke it (the destroy request had no `password` field to satisfy the new `required|current_password` rule) — fixed as part of adding the list filters below, since both changes touched the same view. On failure, Laravel's standard `current_password` French message ("Le mot de passe est incorrect.", already in `lang/fr/validation.php`) surfaces via `@error('password')` like any other validation error — no accord data is touched.
  - **Étape 3 (envoi puis signature)**: `AccordController::envoyer` just stamps `envoye_le` (a tracking checkbox, confirmed **not** to send a real email — no destinataire email is captured anywhere). `AccordController::signer` takes `date_signature` (defaults to today if blank) + `duree_valeur`/`duree_unite` (`ans`/`mois`) and stores a computed `date_expiration` (`Accord::calculerDateExpiration()`) rather than trusting manual input; it also optionally accepts a `fichier_signe` upload (`chemin_fichier_signe`/`nom_fichier_signe`, mirrors the reception file pattern) — needed for the AI compliance role below. There's no UI to add/replace this file after the initial signing submission (a known gap, not yet requested to be closed).
  - **Alerte d'expiration**: `App\Console\Commands\NotifierAccordsExpirants` (`accords:notifier-expiration`, scheduled daily in `bootstrap/app.php`'s `withSchedule()`) mails every active user once per accord when `date_expiration` falls within 60 days — `alerte_expiration_envoyee_le` is stamped on send so the same accord is never re-notified.
- **Accords — agent IA (Gemini, palier gratuit)**: `App\Services\GeminiClient` is a thin HTTP wrapper around Gemini's `generateContent` endpoint (`config('services.gemini.key'/'model')`, from `.env`'s `GEMINI_API_KEY`/`GEMINI_MODEL` — no billing, free-tier rate limits apply), forcing `response_mime_type: application/json` so callers get a decoded array back and never hand-parse free text. It accepts an optional inline file (`['chemin' => ..., 'mimeType' => ...]`, base64-encoded into the request) — Gemini reads PDF/PNG/JPEG natively (including scanned/handwritten content via vision), but **not** `.doc`/`.docx` directly; for those, both AI services extract plain text via `PhpOffice\PhpWord\IOFactory::load()` and inline it into the prompt instead (best-effort, wrapped in try/catch — falls back to metadata-only context on failure, e.g. legacy `.doc` files PhpWord's Word2007 reader can't parse). Every controller call is wrapped in try/catch so a Gemini failure (bad key, quota, transient 503) surfaces as a readable flash/JSON error instead of a 500 — confirmed live: an actual `GEMINI_API_KEY` was tested end-to-end (JSON-mode round trip succeeded) after fixing a local environment issue (see PHP version note below on `curl.cainfo`/`openssl.cafile`, unrelated to the app code). `GeminiClient::genererJson()` calls `set_time_limit(200)` before the HTTP call, comfortably above its own `Http::timeout(60)` (× up to 3 attempts, see below) — without it, a Gemini call slower than PHP's `max_execution_time` (30s by default) gets killed by a PHP-level fatal timeout *before* Guzzle's own timeout or our try/catch ever get a chance to run, since that kind of engine-level timeout is not a catchable `Throwable`; the symptom in the UI was a generic "La génération IA a échoué." with no detail (the JS's hardcoded fallback, since the response was never the controller's own JSON error shape). A multimodal call with a real file attachment can legitimately take over 30s, so this is a normal, expected occurrence rather than an edge case. Once that fix let the real Gemini error surface, it turned out to be the free tier's other common failure mode: a transient `503 UNAVAILABLE` ("this model is currently experiencing high demand"). `GeminiClient::appellerAvecNouvellesTentatives()` retries automatically up to 3 times (1s apart, both tunable via the constructor's `$delaiEntreTentativesMs` — tests pass `0` to stay fast) specifically for a 503 status, and only for that status — a bad key, quota error, or any other 4xx/5xx still fails immediately, on the first attempt, with no retry. Tests never call the real API — `GeminiClient` is constructor-injected everywhere so `$this->mock(GeminiClient::class, ...)` (Feature tests) or a direct `Mockery::mock()` instance (Unit tests) replaces it.
  - **Rôle 1 — pré-remplissage de la fiche d'appréciation**: `App\Services\AccordAppreciationSuggestionGenerator` builds a prompt from a **fixed** set of few-shot examples — `App\Models\AccordAppreciationExemple` (`AccordAppreciationExemple::orderBy('ordre')->get()`, no `limit()`), 4 rows transcribed verbatim from real DCUS fiches and seeded via `Database\Seeders\AccordAppreciationExempleSeeder` — plus the target accord's own file, and asks Gemini to return 4 content fields (`origine`/`objet`/`observations_forme`/`observations_fond`, in the `- `/`  - ` bullet convention `FicheAppreciationGenerator` already understands) — deliberately excluding `avis` (a human-assigned identifier, not content) and the Conclusion (fully computed, see above). **This replaced an earlier version that pulled the 5 most recently-saved `AccordAppreciation` records** as examples — an explicit user decision (2026-09-10) to keep the style of reference fixed and DCUS-curated rather than letting it drift with whatever agents happen to submit; `AccordAppreciationExemple` rows are deliberately **not** linked to any real `Accord` (no `accord_id` — the prompt never used accord fields for the examples anyway, only the 4 content fields), so seeding them doesn't pollute the real `accords.index` list. No separate legal corpus is used for the underlying legal knowledge; the model relies on its own general knowledge of Beninese law, per explicit user decision, and the prompt tells it to stay generic rather than invent specific articles. Triggered by an explicit **"Générer avec l'IA"** button on `accords/appreciation.blade.php` (not automatic on page load, to avoid an API call on every visit) — `POST accords/{accord}/apprecier/suggestion` (`AccordAppreciationController::suggerer`, same `apprecier` policy as the real submit) returns JSON that plain `fetch()` JS drops straight into the existing form fields' `value`, which the agent is then free to edit before the normal `store()` submit — nothing from this endpoint is ever persisted directly.
  - **Rôle 2 — analyse de conformité du document signé**: once `chemin_fichier_signe` is set, an **"Analyser la conformité"** button appears (`accords.show`, sidebar, `canManage()`-gated same as `signer()`) — `POST accords/{accord}/analyser-conformite` (`AccordConformiteController::analyser`). `App\Services\AccordConformiteAnalyzer` prompts Gemini with the appreciation's `observations_forme`/`observations_fond` plus the signed file, asking which observations were addressed (deliberately excludes `avis`, since that's just the fiche's identifier, not judgment content, and excludes the Conclusion, since it's boilerplate that carries no per-accord analytical signal); requires an existing appreciation and a signed file (throws a descriptive `RuntimeException` otherwise, caught and flashed). Result is stored via `$accord->rapportConformite()->updateOrCreate([], ...)` — one report per accord, **AccordRapportConformite`** (`resume`/`points_conformes`/`points_non_conformes`/`chemin_rapport_word`/`genere_par`/`genere_le`), re-running the analysis edits it in place and deletes the previous `.docx`. `App\Services\RapportConformiteGenerator` builds that `.docx` directly with PhpWord and **reproduces exactly the same gabarit as `FicheAppreciationGenerator`** (explicit DCUS requirement — "le rapport final doit garder le même template que la fiche d'appréciation"), not its own bespoke layout as before: same ministry letterhead, same title convention (`strtoupper("RAPPORT DE CONFORMITÉ DU PROJET D'".$accord->titre)`, mirroring the fiche's `"FICHE D'APPRÉCIATION DU PROJET D'".$accord->titre`), same single bordered table (Accord/Référence/Date de signature/Résumé/Observations prises en compte/Observations non prises en compte — one row per field), same footer. This shared structure — `ajouterEnTete()`, `ajouterLigneChamp()`, `ajouterLigneObservations()`, the reduced-margin section factory, and the Trebuchet MS defaults — lives in `App\Services\Concerns\ConstruitDocumentDcus`, a trait used by both generators (extracted from `FicheAppreciationGenerator` when the rapport was unified onto its template), alongside the pre-existing `App\Services\Concerns\RendDesParagraphesAvecPuces` (bullet-list parsing) and `App\Services\Concerns\AjoutePagination` (same pattern — shared traits rather than duplicated code between the two generators): a centered "Page {PAGE} sur {NUMPAGES}" footer built from native Word `PAGE`/`NUMPAGES` fields (`Footer::addPreserveText()`), so the page count updates dynamically as Word paginates the document rather than being computed once at generation time — an explicit DCUS requirement, all generated documents must be paginated. **Police** : both generators set `PhpWord::setDefaultFontName('Trebuchet MS')`/`setDefaultFontSize(12)` (via `ConstruitDocumentDcus::nouveauDocumentOfficiel()`) for all body text, with each document's own title line explicitly bumped to `size: 14` — an explicit DCUS requirement, the only size-14 text in either document. Downloadable via `accords.rapports-conformite.telecharger` (mirrors the appreciation-fiche download pattern, including the same `/`-in-filename sanitization fix).
- **PDF/export**: uses `barryvdh/laravel-dompdf` (`app('dompdf.wrapper')`) rendering blade views under `resources/views/exports/`. CSV export (`ExportController::accordsCsv`/`reunionsCsv`, routes `exports/{reunions,accords}/csv`) is hand-rolled with `phpoffice/phpspreadsheet`'s `Writer\Csv` directly (`app/Exports/AccordsExport.php`/`ReunionsExport.php`) — there is **no** `maatwebsite/excel` dependency, despite those class names/shapes looking like it; don't reintroduce `FromCollection`/`WithHeadings`-style Concerns interfaces, they won't resolve. `CodirController::generatePdf` / `ReunionController::generatePdf` render single-record PDFs.
- **CODIR access control**: beyond role checks, `Codir` has a per-user allowlist for downloading rapports/PDFs — `CodirAcces` model + `Codir::userPeutTelecharger($userId)`, enforced via `CodirPolicy::download`. Admins bypass this check.
- **Archives**: a private, per-user file-organization space — not shared like the rest of the app. `ArchiveFolder` (self-referencing `parent_id`, infinite nesting) and `ArchiveFichier` (belongs to a nullable `folder_id`, i.e. root-level files are allowed) are both scoped by `user_id`; `ArchiveFolderPolicy`/`ArchiveFichierPolicy` check `user_id === $user->id` only — no `canManage()`, no admin bypass, unlike every other resource in this app. Deleting a folder cascades at the DB level (`cascadeOnDelete` on `parent_id`/`folder_id`) but the controller (`ArchiveController::destroyDossier`) must walk `ArchiveFolder::fichiersRecursifs()` first to delete the physical files from `Storage::disk('public')` before the row cascade fires. The add-file form (Intitulé/Numéro/Description/fichier) has no date input — "date et heure" is just `created_at`, shown after saving.
- **Archives — partage**: sharing a file creates an **independent copy** in the recipient's own Archives space (`ArchivePartageController::store`, `Storage::disk('public')->copy(...)`) — not a live access grant. Once delivered, the copy is a normal `ArchiveFichier` owned by the recipient, subject to the exact same policy as everything else in Archives. `ArchivePartage` (`fichier_original_id` nullable/`nullOnDelete`, `fichier_copie_id`/`cascadeOnDelete`) is a history log, not a live grant; `ArchiveFichier::partageOrigine()` (`hasOne` keyed on `fichier_copie_id`) surfaces "Partagé par X" on a received copy without duplicating data. Revoking a share (`ArchivePartagePolicy::delete`, sender-only) deletes only the history row — never the recipient's already-delivered copy. `FichierPartageNotification` is a regular (non-on-demand) notification (mail + database channel), since the recipient is already a `User`/`Notifiable`. Route-order note: `GET archives/partages` is declared before `GET archives/{dossier?}` in `routes/web.php` since both match a single path segment. Each file also has an inline preview (`ArchiveController::apercuFichier`, `Storage::disk('public')->response(...)`, `Content-Disposition: inline`) alongside download — same `view` policy check, opened via `target="_blank"`, no separate viewer/library involved (the browser renders what it can, downloads the rest). Both `archive_partages` and `archive_dossier_partages` have a nullable `note` column — one optional free-text note per share request (applies to every file/folder in that submission), surfaced in the recipient's email just before the download button.
- **Archives — partage de dossier**: mirrors file-sharing but for `ArchiveFolder` via a parallel `ArchiveDossierPartage` model/table (kept separate from `archive_partages` rather than adding nullable columns there, since `doctrine/dbal` isn't installed and Laravel can't `->nullable()->change()` an existing column without it). Sharing a folder recursively recreates its *entire* subtree (subfolders + files) under a new folder — auto-renamed with a `" (2)"`-style suffix (`nomDossierDisponiblePour`) on collision, since Archives enforces no-duplicate-sibling-names everywhere else. Separately, a `.zip` snapshot of that copy is built with PHP's `ZipArchive` (`genererZipDossier`/`ajouterDossierAuZip`) and stored under `archives/dossier-partages/` — this zip is **not** listed anywhere in Archives itself, it exists solely so `DossierPartageNotification`'s email can link straight to a one-click download (`archives.dossier-partages.telecharger`, gated by `ArchiveDossierPartagePolicy::download` — recipient only, unlike `delete` which stays sender-only). Revoking a folder share deletes the zip file plus the log row, never the recipient's already-copied folder.
- **Archives — dossier collecteur "Partages reçus"**: every file-copy and folder-copy delivered to a recipient (via either share flow above) lands inside an auto-created root-level folder named `Partages reçus` in *their* Archives, instead of directly at the root — `ArchivePartageController::dossierPartagesRecusPour()` (`ArchiveFolder::firstOrCreate(...)`) creates it lazily on the recipient's first-ever received share and is reused for every subsequent one. The folder-name-collision check (`nomDossierDisponiblePour`) is scoped to inside this folder, not the root.
- **Archives — glisser-déposer**: `archives/index.blade.php` makes file/folder rows `draggable`, and folder rows plus non-active breadcrumb crumbs (including "Racine") into drop targets (`.drop-cible`, `data-dossier-id`); a plain HTML5 drag/drop handler in a `@push('scripts')` block does a `fetch(..., {method: 'PATCH'})` to `ArchiveController::deplacerFichier`/`deplacerDossier` on drop, then `location.reload()` — no JS framework, no client-side state. Both actions re-check the same `update`/`view` policies as the rest of Archives (source item + destination folder must both belong to the user). `deplacerDossier` additionally guards against circular moves (dropping a folder into itself or one of its own descendants) via the new `ArchiveFolder::descendantsRecursifs()` and reuses `nomDejaPris()` for the destination name-collision check — same "no duplicate sibling names" rule as create/rename. `layouts/app.blade.php` gained a `<meta name="csrf-token">` tag (previously absent) so this `fetch` call can send `X-CSRF-TOKEN`.
- **In-app notifications (Dashboard)**: uses Laravel's *built-in* database notification channel — `User` already had `Notifiable`, so this only needed the standard `notifications` table migration (uuid `id`, polymorphic `notifiable`, `data` json, `read_at`), no new model. `FichierPartageNotification`/`DossierPartageNotification` gained `database` alongside `mail` (their `toArray()` includes the optional share `note`). Four new **database-only** notifications — `ReunionCreeeNotification`, `DecisionCreeeNotification`, `AccordCreeNotification`, `AccordStatutChangeNotification` — are dispatched directly from `ReunionController::store`, `DecisionController::store`, `AccordController::store`/`updateStatut` to `User::actifsSauf(Auth::id())` (every active user except the actor); deliberately mail-less to avoid extra Brevo load for routine activity. Every `toArray()` follows the same shape (`type`, `icone`, `message`, `url`, and `note` for shares) so the Dashboard can render them polymorphically. `NotificationController::marquerLu`/`marquerToutLu` (routes `notifications/{id}/lire`, `notifications/tout-lire`) mark read via Laravel's built-in `$user->notifications()`/`unreadNotifications`/`markAsRead()` — `marquerLu` looks the notification up scoped to `$request->user()->notifications()` (404s on another user's id) and redirects straight to its `data['url']`.
- **Mail classes**: `app/mail/` (lowercase, note the non-standard casing — not PSR-4 for that reason, composer prints a "does not comply with psr-4" warning on every `dump-autoload`, harmless but expected) holds `ConvocationCodir` and `ConvocationReunion` mailables plus a shared `convocation.blade.php` template, used to notify participants of scheduled meetings. `App\Notifications\ResetPasswordNotification` (proper PSR-4 location) is the password-reset email, in French — `User::sendPasswordResetNotification()` is overridden to use it instead of Laravel's default English notification.
- **Views**: Blade templates under `resources/views/`, one directory per resource (`codirs/`, `reunions/`, `decisions/`, `accords/`, `utilisateurs/`, `exports/`, `email(s)/`), plus shared `layouts/`. No frontend framework — Tailwind v4 + Vite, no Livewire/Inertia. Auth pages (`login`, `forgot-password`, `reset-password`) are standalone full-page Blade files (don't extend `layouts/`), styled with Bootstrap 5 + Bootstrap Icons via CDN, not Tailwind.
- **Translations**: `lang/fr.json` overrides a handful of English strings baked into Laravel's default notification/mail Blade components (`__('All rights reserved.')` etc.) — `resources/views/vendor/` is intentionally *not* published/frozen; the JSON translation applies to the framework's own vendor views without needing a local copy. `lang/fr/validation.php` is a full French translation of Laravel's validation messages (plus a French `attributes` map) — this app has `APP_LOCALE=fr` with no `APP_FALLBACK_LOCALE=en` fallback file existing either, so without this file **any** unhandled validation rule failure (e.g. `unique`, `min`, `in` — anything without a custom message) renders the raw un-translated key (`"validation.unique"`) straight to the page. Keep this file in sync (attribute names especially) when adding new form fields.
